# The `kanbei` private-data VM

Smortress's third microVM (`smores56/sdlc#584`, part of #509). It is NIC-less,
gets the RTX 3090 by VFIO passthrough, keeps its state on a LUKS2 volume inside
the guest image, and is sealed to a per-VM software TPM. Host-side operator
steps are in [`docs/manual-steps.md`](manual-steps.md) (`host/smortress`, under
"Kanbei private-data VM"); the threat model is in
[`docs/kanbei-split.md`](kanbei-split.md).

Everything is behind `kanbeiVm.enable` (default `false` in
`modules/hosts/smortress/default.nix`). While it is off the host still runs
Immich and `llama-cpp` on the GPU and this module adds nothing but the option.
With it on, `nvidia.nix` and `llm.nix` become inert
(`lib.mkIf (!config.kanbeiVm.enable)`) — the files stay until T9 deletes them,
but nothing loads the driver or runs `llama-cpp`. An
assertion fails evaluation if the enabled host would still load `nvidia` or
run `llama-cpp`.

## Hardware facts (discovered, not guessed)

| Function | PCI path | ID | IOMMU group |
|---|---|---|---|
| RTX 3090 | `0000:08:00.0` | `10de:2204` | 16 |
| GA102 HDA (HDMI audio) | `0000:08:00.1` | `10de:1aef` | 16 |

Both functions are alone in group 16, so no `pci-stub` and no ACS override are
needed. `modules/nixos/kanbei-vm.nix` records this as `pci`; evaluation asserts
the VFIO id list matches it exactly, so a moved card has to be re-discovered
rather than silently half-passed.

Host binding, only while enabled:

```nix
boot.kernelParams = [ "amd_iommu=on" "iommu=pt" "vfio-pci.ids=10de:2204,10de:1aef" ];
boot.initrd.kernelModules = [ "vfio" "vfio_iommu_type1" "vfio_pci" ];
boot.extraModprobeConfig = "softdep snd_hda_intel pre: vfio-pci";
```

The microvm runner also unbinds and re-probes both functions (`pci-setup`) and
hands `/dev/vfio/16` to `microvm:kvm` before QEMU starts.

Runtime check on the host (also `kanbei-vm-verify`, a oneshot that runs after
the guest starts):

```sh
for d in 0000:08:00.0 0000:08:00.1; do basename "$(readlink -f /sys/bus/pci/devices/$d/driver)"; done
ls /sys/kernel/iommu_groups/16/devices     # exactly the two paths above
sudo dmesg | grep -i -e iommu -e vfio      # no ACS override, no "group is not viable"
lsmod | grep nvidia                        # empty
```

## The guest

| | |
|---|---|
| runner | qemu, `microvm` machine, `pcie=on` |
| cpu/mem | 8 vcpu, 8192 MiB |
| network | none — `microvm.interfaces = [ ]`, no tap, no firewall rules |
| vsock | cid 4 (asserted unique across guests); the inference lanes stay loopback-only, the host relay is T14's |
| disk | one raw image `data.img` (`serial=kanbei-data`, 64 GiB, created by `preStart`), `/dev/disk/by-id/virtio-kanbei-data` |
| console | guest serial on QEMU stdio → `StandardOutput=append:` a root-only file |
| host store | `/nix/store` virtiofs, read-only, `registerClosure = false` |

Shares (virtiofs):

| tag | host source | guest | mode |
|---|---|---|---|
| `ro-store` | `/nix/store` | `/nix/store` | ro |
| `inbox` | `/var/lib/data/inbox` | `/mnt/kanbei/inbox` | ro |
| `vault` | `/var/lib/data/vault` | `/mnt/kanbei/vault` | ro |
| `todo` | `/var/lib/data/todo` | `/mnt/kanbei/todo` | rw |
| `kanbei-secrets` | `/var/lib/kanbei-vm/secrets` | `/run/kanbei-secrets` | ro |
| `kanbei-enroll` | `/var/lib/kanbei-vm/enroll` | `/mnt/kanbei-enroll` | rw |

`vault` and `todo` translate guest uid 1000 (the payload) and the agent kernel's
own uid 1001 (`modules/lib/kanbei-agent.nix`) to the host `vault` user (981),
which owns both trees; guest root maps to `nobody`. The agent kernel
(`modules/nixos/kanbei-agent.nix`) therefore writes Todo and reads the vault as
`vault` without running as root, while a future sandbox keeps uid 1000. The
`inbox` tree is 0750 root with 0600 batches and no translation for uid 1000: the
inbox share maps only the kernel uid to host root (and guest root to `nobody`),
so the payload uid and every other non-root uid cannot read a batch directly.
Guest root can always assume the kernel uid; the mapping keeps the payload
identity out, not a privileged one. No identity maps to host root except that
one read-only inbox grant. The
guest's `/var/lib/kanbei` LUKS mount is `0750 root:kanbei` (the kernel joins the
`kanbei` group to traverse it); `phone-state` is `0750 root:kanbei`; every secret
file stays `0400`/`0600` root inside a `0700` directory. `kanbei-enroll` is the
guest's one host-writable path (root-only 0700, nothing on the host reads it
except the operator).

The host-side relay token (`/var/lib/kanbei-vm/secrets/relay-token`, 0400 root) is
generated by `kanbei-vm-prep` and shared read-only into the guest; the chat relay, the
ACME responder, the age-recipient listener and the search relay all authenticate with
it (see `docs/kanbei-access.md` and `docs/kanbei-ingest.md`).

The guest's inference lanes (`modules/nixos/kanbei-inference.nix`, T11) run as
that uid 1000: one GPU `llama-server` for chat and two CPU servers for
embeddings/reranking, all on `127.0.0.1`. The weights are data on the LUKS
volume (`/var/lib/kanbei/models`), not in the store, so a rebuilt guest never
re-downloads 14 GiB. `docs/kanbei-inference.md` has the pool math, flags, eval
protocol and residuals; the download/verify procedure is step 6 of the operator
steps above.

### The agent kernel

`modules/nixos/kanbei-agent.nix` installs the `kanbei` flake input (pinned to the
same nixpkgs rev, `inputs.nixpkgs.follows = "nixpkgs"`) and runs it as
`kanbei.service` under the dedicated `kanbei-core` uid 1001. The unit carries the
whole `KANBEI_*` boot contract from `kanbei/src/main.ts:171-256`; the two
loopback listeners are chat `8080` and status `8081` (inference owns 8090-8092).

- `/etc/kanbei/manifest.json` and `/etc/kanbei/posture.json` are generated from one
  Nix attrset. The posture is `addresses = ["lo"]`, `enforcement = none`, and the
  manifest requires `none` as well: no cgroup or Monty verifier exists yet, so a
  stronger claim would defeat the startup check.
- `kanbei-age-identity.service` creates the age identity on the LUKS volume
  (`/var/lib/kanbei/agent/age/identity.txt`, 0400 kernel uid) and its recipient.
  `kanbei-age-publish.service` sends the recipient, after the shared relay-token
  line, to host CID 2 port 7100 and retries until the ingest listener has it. The
  root-only relay token reaches both units as a systemd credential; the vendored
  Deno wrapper is extended locally with the `/run/credentials` read root.
- The agent dials `/run/kanbei/csr.sock` and `/run/kanbei/search.sock`. Deno has
  no AF_VSOCK transport, so `kanbei-csr-bridge` and `kanbei-search-bridge` splice
  each UDS stream to host CID 2 ports 10001 and 7101. The bridges run as the
  kernel uid and bind 0600 sockets in a 0700 `/run/kanbei` before the kernel
  starts, so only the trusted kernel can reach a host channel.
- `kanbei-logs` includes `kanbei.service` in its journal inventory.

**Decision (deferred):** `kanbei-ui` still posts chat straight to the local
llama.cpp lane on `127.0.0.1:8090`; it does not route through the agent chat
lane yet. The UI's TLS/auth surface is T14's, and repointing it now would change
the consent/session path before that surface exists. The kernel is nonetheless
given `KANBEI_CHAT_UPSTREAM` at the same lane so the agent chat channel answers
when exercised directly. Reconcile the UI path in a follow-up.

**Tuta is one origin.** `KANBEI_ORIGINS` is the kernel's `OriginId` set
(`tuta,tuta-mail,tuta-calendar,finance,brave,immich,phone,cluster-digest`). The
host writers emit `tuta` for both mail and calendar — one bridge, one secret —
and the kernel accepts it alongside the unused split ids. The kernel also ignores
an unknown key inside a heartbeat instead of quarantining the envelope, so one
stray id can no longer leave every source `unknown`.

The `kanbei` flake input is a private repository fetched over SSH. Flake inputs
are resolved even when `kanbeiVm.enable` is off, so every evaluation of this
checkout (including the other hosts) now needs SSH access to
`smores56/kanbei`. Making the input public or adding a read-only mirror is a
separate decision.

## vTPM and what the seal binds to

microvm.nix has no TPM option. `kanbei-swtpm.service` runs
`swtpm socket --tpm2 --tpmstate dir=/var/lib/kanbei-vm/swtpm` as root with the
state a 0700 root directory and one control socket in `/run/kanbei-vm` (0750
`root:kvm`, socket 0660) so the `microvm` user cannot read the NVRAM but can
connect. QEMU's emulator backend speaks the whole swtpm protocol (control and
TPM traffic) on that `--ctrl` channel; give it a `--server` data socket instead
and QEMU blocks in its first read before any CPU starts. It attaches from
`microvm.qemu.extraArgs`:

```
-chardev socket,id=chrtpm,path=/run/kanbei-vm/swtpm.ctrl
-tpmdev emulator,id=tpm0,chardev=chrtpm
-device tpm-crb,tpmdev=tpm0
```

`microvm.preStart` refuses to start the guest if that socket is missing, so a
dead swtpm can never boot a guest that will then fail its unlock. The state
survives reboots and unit restarts and is never in a restic path (asserted).

The guest boots with `-kernel`/`-append` (no firmware), so there is no secure
boot and no measured boot, and the TPM2 token is enrolled with **no PCR
policy** (systemd 261's default). What the seal binds to is only the swtpm's
state — its endorsement/SRK material and the systemd token in the LUKS header:

- The swtpm state is preserved → a kernel, initrd or NixOS generation change
  does not touch the seal, so a rebuild never strands the unlock.
- The swtpm state is lost, replaced or restored from a different instance → the
  TPM will not unseal, and only the recovery key opens the volume.

An unbound token also means a *copy* of the image plus `/var/lib/kanbei-vm/swtpm`
unlocks elsewhere. Both are root-only host artifacts, and host root already
reads every guest disk (`docs/kanbei-split.md`), so this does not widen the
threat model; it is the price of "a kernel rebuild never strands the unlock".

Restoring an image backup therefore needs the recovery key when the swtpm state
is also lost; with both the image and `/var/lib/kanbei-vm/swtpm` recovered, the
TPM unlock works again.

## In-guest disk and first-boot enrollment

`kanbei-data-open.service` opens the volume in stage 2: on first boot it
formats the virtio-blk device as LUKS2, enrolls the vTPM token, opens the
mapping and makes the ext4 filesystem; on later boots it opens the mapping with
the TPM2 token and falls back to the escrowed recovery key when the swtpm state
is gone.

`/etc/crypttab` is deliberately empty and `/var/lib/kanbei` is declared as a
`systemd.mounts` entry rather than a `fileSystems` entry. A crypttab volume and
every `.mount` unit are ordered before `local-fs.target`, while the recovery
contract and escrow live on virtiofs shares that systemd mounts after it;
putting the unlock in the early boot deadlocks the first boot. The mount is
ordered `After=kanbei-data-open.service` and `Before=kanbei.service`.

First boot (`modules/nixos/kanbei-vm.nix`, `guestInit`):

1. Waits for the virtio-blk device. If it already carries a LUKS header it
   enrolls the TPM2 token from the escrowed key when the token is missing, then
   opens the mapping with the token (escrow as fallback).
2. Otherwise it picks the recovery credential **before** formatting: the sops
   contract `/run/secrets/kanbei-recovery-key` when present (copied by
   `kanbei-vm-prep`), else an escrowed key at
   `/var/lib/kanbei-vm/enroll/recovery.key` (0600, root-only) created first, or
   reused from a previous partial run.
3. `cryptsetup luksFormat --type luks2 --label KANBEI --key-file <recovery>`.
4. `systemd-cryptenroll --tpm2-device=/dev/tpm0` (no PCR policy) with
   `--unlock-key-file=<recovery>`; the escrowed key is the recovery credential,
   so no separate systemd-generated one is enrolled. The command runs under a
   timeout with stdin closed, and every step is echoed to the serial console
   (the guest journal is volatile).
5. Opens the mapping and runs `mkfs.ext4` only if the mapping has no ext4
   signature yet.

Because the recovery credential exists before the format, a crash anywhere in
that sequence is recoverable with it — the volume is never formatted under a
key nobody kept.

`/run/secrets/kanbei-recovery-key` is a **contract**, not a registered sops key
yet: `secrets/smortress.yaml` has no such key (it cannot be encrypted from this
checkout), so `docs/manual-steps.md` carries no `secret/kanbei-recovery-key`
anchor and the host prep unit simply skips the copy. Registering the key is a
manual step: add it with `sops secrets/smortress.yaml`, declare it in
`modules/hosts/smortress/secrets.nix`, and add the anchor.

After the first successful TPM boot, store
`sudo base64 -w0 /var/lib/kanbei-vm/enroll/recovery.key` in the password manager
(the escrow holds raw bytes, so the stored form is base64) and delete the escrow;
a re-format is then impossible without that key, which is the point.
`docs/manual-steps.md` steps 3, 4 and 6 decode it back for host-side unlocks.

## Console

`microvm@kanbei.service` writes QEMU's stdio (the guest serial console) to
`/var/lib/kanbei-vm/console/console.log` via `StandardOutput=append:`. systemd
opens it as root, the parent is 0700 root, and `-monitor none` keeps the guest
away from the QEMU monitor. Nothing else on the host reads it.

## Backup and restore

`services.restic.backups.kanbei-r2` and `kanbei-local` snapshot only
`/var/lib/microvms/kanbei/data.img` — the LUKS2 ciphertext — nightly at 02:30
and 02:40. Both run `kanbei-freeze` (`modules/lib/kanbei/freeze.py`) in
`backupPrepareCommand`/`backupCleanupCommand`. The helper refcounts jobs under a flock
in `/var/lib/kanbei-vm/backup/backup-refs.json` (durable: stopping the VM also removes
swtpm's `/run` directory, so the marker cannot live there): the first prepare stops
`microvm@kanbei.service` (graceful ACPI powerdown) and the last cleanup restarts it, so
one job's cleanup cannot start the guest while the other still snapshots. A job that
dies without its cleanup expires after 12 hours; `kanbei-freeze --job <id> --reset`
clears a stuck refcount. The swtpm state, the console log, the inbox and the escrow are
excluded (the swtpm exclusion is asserted).

Restore:

1. Stop the guest: `sudo systemctl stop microvm@kanbei.service`.
2. Restore the image from restic (any repo) to
   `/var/lib/microvms/kanbei/data.img`, owned `microvm:kvm`, mode 0600.
3. Restore `/var/lib/kanbei-vm/swtpm` only if you archived it by hand (it is
   deliberately not in any backup). Without it the TPM unlock fails.
4. Start the guest and read the console; with a lost or mismatched swtpm the
   volume stays locked, so unlock it with the recovery key as below.

`kanbei` units deliberately carry no `onFailure = [ "cloudflare-email@%n" ]`:
the alert template is a host service on smortress and the split must not make
the private-data guest depend on the host's tunnel or mail path. A failed
backup is visible in the journal (`journalctl -u restic-backups-kanbei-r2`)
until kanbei gets its own alerting; evaluation asserts no `kanbei*` unit has
that `onFailure`.

## Recovery procedures

The image is a LUKS2 container over a plain file, so the primary recovery path
runs on the **host** with the guest stopped and needs no TPM and no guest
console:

```sh
sudo systemctl stop microvm@kanbei.service
sudo cryptsetup open --key-file /var/lib/kanbei-vm/enroll/recovery.key \
  /var/lib/microvms/kanbei/data.img kanbei-data
sudo mount /dev/mapper/kanbei-data /mnt            # inspect / repair

sudo umount /mnt
sudo cryptsetup close kanbei-data
```

With the contract key (or a printed `--recovery-key`) instead of the escrow
file, omit `--key-file` and paste it at the prompt. The swtpm is not involved,
so this works even when the TPM state is gone.

An interactive guest console is only needed to re-enroll the TPM. The unit
sends the serial console to a write-only root-only file, so run the same runner
by hand as the VM user (the virtiofs daemons must be up; `swtpm` is already):

```sh
sudo systemctl stop microvm@kanbei.service
sudo systemctl start kanbei-swtpm.service microvm-virtiofsd@kanbei.service
sudo -u microvm bash -c 'cd /var/lib/microvms/kanbei && exec ./current/bin/microvm-run'
# The monitor is disabled, so leave with `poweroff` in the guest shell; otherwise
# `sudo pkill -u microvm qemu-system-x86_64` from another terminal.
```

Re-enroll the TPM after a swtpm state loss (in that guest shell, volume
unlocked with the recovery key) so the next boot is unattended again:

```sh
systemd-cryptenroll --wipe-slot=tpm2 --tpm2-device=auto \
  --unlock-key-file=/run/kanbei-secrets/kanbei-recovery-key \
  /dev/disk/by-id/virtio-kanbei-data
```

Keep a header backup off the image after the first boot (`cryptsetup
luksHeaderBackup ... --header-backup-file`): the LUKS2 header lives at the start
of `data.img`, so a truncated or corrupted image is recovered by restoring that
header first.

## Cutover (one-time, hardware-gated)

The full procedure is in `docs/manual-steps.md` ("Kanbei private-data VM").
It is a single switch that: stops Immich and `llama-cpp`, unbinds `nvidia`, lets
the kernel claim both functions for `vfio-pci`, and boots the guest. Nothing
above is exercised by an eval or a build, so it must be done with the operator
present and the recovery key in hand.
